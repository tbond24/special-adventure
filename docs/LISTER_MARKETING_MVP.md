# Lister acquisition and journey analytics

## Existing system and scope

Vacancy already had `analytics_events`, database listing status-change logs, an MFA-gated Admin area, and a three-screen listing journey: Location, Listing details (including media and pricing), Review. This release reuses those systems. It adds only one visible section, Admin → Marketing. No marketplace, listing form, authentication, navigation, card, search, or property-page markup or styling changes are part of this release.

The release checkpoint is Git tag `rollback/before-lister-marketing-20261004` at `066ead2`. Database migrations are additive to the existing analytics table and do not alter listing or auth records.

## Data and triggers

`lister_session_started` and `lister_landing_viewed` fire once per browser session. `list_property_clicked` fires on the List navigation or Create new listing control. `property_type_completed` fires when a listing category is chosen. `listing_started` and `location_started` fire when the current listing form opens. `location_completed`, `listing_details_completed`, `photos_completed`, and `pricing_completed` fire only when the existing Continue validation allows the next screen. `listing_previewed` fires on entering Review. `step_ready` records the time from Continue click until the next step appears. `publish_clicked` fires on form submission. `listing_record_created` fires after the create RPC returns an ID. `photo_upload` records upload completion and duration. `listing_submitted` fires only after the existing reconfirm RPC succeeds. `journey_error` records signup, listing-save, upload, or publication failure categories. `signup_started`, `signup_pending_confirmation`, and `signup_completed` follow existing email/guest-upgrade calls; email confirmation after a pending signup is not yet separately observed.

The authoritative publication metric is **not** a browser event. Admin reporting reads the first transition of each listing to `active` from `listing_activity_log`. A property's first publication is the earliest such transition across its units. Attribution is linked only to a matching listing event written under that property's owner account. Publications without that link are marked unknown.

New event fields are event ID, pseudonymous visitor/session/journey IDs, authenticated user ID when present, listing ID when applicable, event time, route, source/medium/campaign and ad IDs from URL parameters, first-touch source/medium/campaign, referrer **hostname**, landing **path**, step, coarse device/browser/OS families, step/upload duration, active duration, and bounded error category. The existing Supabase table stores them. Full referrer URLs, raw IP addresses, precise location, raw user agent, passwords, form text, property address, message content, images, session replay, and Meta credentials are not collected by this feature. No third-party analytics receive these new events.

The browser sends batches of at most 20 events after a short delay. Collection and admin reporting use the existing backend client. Analytics errors are swallowed in the collector; publication and auth do not wait for an analytics response. The database allows anonymous and signed-in inserts under existing row security, deduplicates event IDs, and allows reads only through existing MFA-backed admin authorization. The admin reporting RPC independently enforces that authorization. The repair migration changes duplicate handling after an initial live database test found that `ON CONFLICT` required a row visibility policy anonymous users rightly lack.

## Admin definitions and limits

Marketing has Overview, Funnel, Sources, Performance, and Errors views, with date, source, campaign, and device filters. Overview counts observed visitor/session IDs, listing starts/submissions, database-confirmed listings, and first property publications. Funnel percentages require observed events for the same visitor at every preceding stage within the selected window; this is deliberately conservative and cannot exceed 100% from unrelated cohorts. Sources separates source and medium so paid and organic visits are distinguishable when tagged. Performance shows browser-measured median and p95 timings and device/browser groups. Errors shows affected sessions and categories by step/device/browser. Timelines show selected session events and linked confirmed publications. The dashboard does not infer that an error caused abandonment.

Counts begin when the collector is deployed; historical traffic cannot be reconstructed. The dashboard limits each result set to 5,000 rows and warns that larger result sets are partial. Attribution may be missing when browser storage is unavailable, a URL loses its UTM parameters, a visitor changes device, an event fails to upload, or publication happened before this release. Source conversion rates compare activity inside a selected time window, not a fully matured cohort. Admin publication totals are authoritative even when attribution is unknown. Meta spend, Pixel/Conversions API, and cost per publication are **not connected**. Existing ad IDs are captured only if provided in the URL. There is no session replay or automated diagnosis.

## Privacy and retention

The new browser identifiers live in first-party local/session storage. Existing Supabase `analytics_events` currently has no automated deletion job; the Marketing UI restricts queries to 90-day windows, but that is **not** a storage-retention guarantee. Before broad traffic acquisition, the operator should set a documented retention period and recurring purge for rows where `event_id IS NOT NULL`, and review Vacancy's privacy notice/consent handling for first-party analytics under applicable law. This release does not change that public-facing notice because the requested UI scope explicitly excludes unrelated pages. The lack of automatic purge is a known limitation, not an asserted privacy-compliance outcome.

## Verification and rollback

Run `VACANCY_E2E_URL=http://127.0.0.1:8765 npx playwright test tests/lister-marketing.spec.js tests/stage101-listing-journey.spec.js tests/stage100-auth-admin.spec.js --project=desktop-chromium --project=mobile-chromium`. Database checks should confirm anonymous/signed-in writes, duplicate event handling, denied non-admin reads, MFA admin read, and that the reporting result has `events` and `publications` arrays. Do not claim live campaign or actual publication conversion validation until representative real traffic exists.

To roll back the UI and collector, redeploy the checkpoint commit `066ead2` or the deployment captured before this release. Database columns and functions can remain inert. Do not drop the shared `analytics_events` table or existing listing activity logs; they predate this feature. If a database rollback is required, revoke the two new RPC grants and remove only the new RPCs, columns/indexes, and new-event rows after reviewing downstream dependencies and preserving a backup.
