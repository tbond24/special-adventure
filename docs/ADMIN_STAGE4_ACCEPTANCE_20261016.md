## Delivered development contracts

**Compatible ingestion:** the exact four public tracking signatures remain: `track_event(text,uuid,text)`, `track_listing_open(uuid,uuid)`, `record_lister_journey(jsonb)` and `record_lister_journey_v2(jsonb)`. Guarded narrowly scoped writers now validate bounded events/fields, derive identity from Auth, normalize routes and scrub acquisition values before using internal insert logic. Existing event-ID deduplication remains; legacy scalar tracking without event IDs is still best-effort, not guaranteed retry deduplication. Direct table and column INSERT grants are revoked only after the compatible writers exist. Private helpers/counters are not client-executable, private tables have RLS and no client grants, and definer functions use empty search paths. Existing customer, owner-metric, message and publication APIs are retained.

One current-minute counter per principal plus global/shared-anonymous counters bounds admitted ingestion. Limits are 6,000 events/minute globally, 1,000 shared unauthenticated events/minute, 600/authenticated principal/minute, with at most 20 events/32 KiB per batch. Locks use an explicit consistent order. Rotating a caller-supplied browser ID cannot bypass the anonymous budget. Authenticated guest accounts are Auth principals, not verified people; the global ceiling still applies. These are database ingestion/data-growth bounds, not a complete network/DDoS defense or a hosted capacity claim. They collect no raw IPs. Known administrators, trusted server-marked tests and recognizable bot user agents are excluded prospectively. A client cannot self-assign identity or trusted exclusion through the payload/user metadata; bot detection remains heuristic and historical anonymous/test coverage remains unknown.

**Collectors and lifecycle:** the current v2 collector uses a 100-event queue, <=20/30 KB batches, three bounded retries, deadlines and account-context checks. Acknowledgements remove only the exact in-flight items; adding events while a batch is pending cannot discard the wrong entries. Oversized heads cannot stall the queue. Original product results/errors remain authoritative and telemetry never holds up a product action. The archived v1 collector source remains identical to the starting checkpoint, avoiding a new dependency for cached old HTML; its RPC is guarded compatibly on the server. Existing 30-second protected recent activity is retained, with no new poller. Main v2 and renter reports are manual, abort obsolete/hidden/account/route reads, discard stale responses and show unavailable/stale rather than zero.

**Lister analytics:** the existing version-2 cohorts, explicit adjacent edges, actual owner/request-ID/publication facts, 7-day observation and grace, 90-day evidence range and 50-summary pagination remain. Known admin/test accounts are excluded from the main v2 cohort/arrival/event paths using server data. Legacy records remain historical; no v1 journey reconstruction, customer-data cleanup or assumed abandonment is introduced. Sessions, browser IDs, creation journeys, requests and listing publications remain separate counting units. Conversion stays unavailable. The report explains prospective/heuristic exclusions and unknown historical coverage.

**Prospective renter analytics:** a separate private table stores only event/session/browser IDs, coarse event names, parent IDs, relevant listing/conversation/actor/owner IDs, notice version and times. No search text, form content, precise address, message body, names, full URLs or raw IPs enter this payload. The actual valid-length Find search action is bound, including keyboard invocation; expanding the magnifier is not a search. Actual public listing opens link to recorded searches; direct entries remain unlinked. An enquiry link requires a real authenticated conversation, its first sender and matching listing/parent/owner. Each conversation links once. First replies come from actual messages by the owner captured at enquiry linkage, within seven days; analytics never creates or edits customer messages. Counts describe searches with linked outcomes and distinct conversations separately, not unique people or completed rentals. Missing links remain unknown and no conversion rate is shown.

Collection defaults **disabled on the server**, with no client-accessible switch to enable it. The implemented opt-in notice/decline/Privacy withdrawal flow is tested in disposal. No renter identifier/event is created before consent; queued unsent collection is suppressed after withdrawal. Existing service analytics remain separate. Thirty-day expiry timestamps and read-window exclusion are implemented; returned evidence bounds disclose clipping to the retained window. **Physical retention deletion is not implemented, scheduled or executed.** Before any real activation, the proposed notice/consent text, applicable privacy requirements and actual 30-day physical retention enforcement need review and separate authorization. Neither an expiry field nor a 30-day report limit is claimed to delete data. This gate is intentional and remains visible as unavailable, not zero, in the report.
