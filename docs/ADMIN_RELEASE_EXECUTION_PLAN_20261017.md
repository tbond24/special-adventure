## Recovery decision after ranking practical options

Treat routine software failure and data disaster separately. **Choose a data-preserving frontend fallback or narrow forward repair for routine release failure**, keeping additive schema, event rows, stronger ingestion/role guards, audit/history and catalogue values. Target no planned lost writes and restoration of usable frontend service within **15 minutes**. Keep a verified private database/media checkpoint before release for failures that really require data recovery. Do not undo stronger guards or restore an old database merely to hide a UI defect.

For disaster recovery, the following ranking weighs customer messages/listings/media, recovery precision, operator burden and current Free-plan cost. This is an engineering recommendation, not a claim that protection is installed or that loss is contractually acceptable.

| Rank | Option | Decision and tradeoff |
| --- | --- | --- |
| 1 | Managed database point-in-time recovery plus separately protected media | **Recommended protection for customer-bearing production.** Avoids operating a frequent full-dump pipeline and supports choosing a point before a damaging write. Paid plan/compute/add-on and a separate media destination/process are needed. Proposed objective: at most **15 minutes** lost committed data/media and service recovery within **4 hours**, proven together by a timed restore drill. Neither objective is a measured guarantee. |
| 2 | Encrypted scheduled offsite database exports with coordinated media snapshots | Lower fixed-platform-cost fallback if paid PITR is declined. Requires an approved private destination/key policy, automation/alerts, consistent recovery sets and drill; time, egress and storage still cost money. An hourly cadence would target up to **1 hour** loss, with the same proposed four-hour recovery objective. Do not silently accept the larger loss window or implement exports under the current boundary. |
| 3 | Daily-only database backup plus media backup | Simpler but risks roughly a day's customer activity between checkpoints; unsuitable as the chosen target when messages/listings can be lost. A fresh pre-release checkpoint is still useful, but is not ongoing protection. |
| 4 | Code rollback without recoverable database/media | Useful only for software recovery. Reject as disaster recovery. Source history cannot recreate customer rows or photo objects. |

**Selected recommendation:** rank 1 for sustained production protection; preserve the no-planned-data-loss routine recovery path. Rank 2 is a separately reviewed cost fallback, not a hidden downgrade. Current implementation is neither: provider metadata identifies no usable completed checkpoint and PITR is false.
