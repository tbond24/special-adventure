# Original listing UI and private account draft browser QA

Run from the repository root:

```sh
npx playwright test --config qa/account-drafts/playwright.config.cjs
```

The server serves this checkout's `app/` on `127.0.0.1:8784`. Playwright boots the real HTML, JavaScript, form controls, auth client, IndexedDB/localStorage code, account draft adapter, and publication wrapper. Set `VACANCY_BROWSER_EXECUTABLE` to use a specific browser. Otherwise the known local headless Chromium is used when present; on other computers and CI, Playwright uses its installed default browser.

## Safety boundary

`synthetic-cloud.cjs` installs a context-wide network handler **before navigation** in every browser context. Local static assets alone use the local server. All auth, REST, Storage, geocoding, remote map assets, and unknown remote requests are fulfilled in memory. WebSockets are closed, service workers blocked. No request creates a hosted account or mutates a hosted database or bucket. User IDs, sessions, listing identities, photo contents, and accounts are synthetic.

The shared in-memory REST/Storage model can be used from two fully separate browser contexts. That lets a fresh device restore the same cloud draft without copying localStorage, sessionStorage, IndexedDB, or browser storage state. HTTP interception remains active in both contexts.

The fixture uses actual account-draft adapter requests; it does not mock `save`, `load`, `list`, `draftRequest`, or account verification. Publication methods are instrumented and call their real implementation after an explicit test-only publish boundary. The draft publication gateway and public-photo uploads are then fulfilled synthetically.

## Coverage

- Original Location → Listing details → Review controls, screenshots, and no new accordion
- Signed-out editing and photos without anonymous signup or cloud draft writes
- Durable local checkpoint, back/cancel, auth failure, same-tab reload
- Password, signup, and OAuth callback account handoffs
- Cloud upload/download byte checks, full commit acknowledgment, and second explicit Publish
- Public upload interruption after the first media link, with retry-all path reuse and no duplicate active photos
- IndexedDB, quota, session-storage, upload, commit, download-integrity failures
- Account autosave and photo-only addition/reordering
- Account dashboard list/resume on a clean second browser context
- Published-listing edit draft resume with original photos plus added private files, followed by explicit Save
- Partial two-unit publication followed by clean-device restore of only the unfinished unit
- Stale-device conflict preserves local work and newer cloud head; saving a separate copy uses new source and unit request IDs
- Account switch while a save is delayed, without cross-account response application
- Ordinary sign-in and the separate anonymous guest enquiry flow
- New fields and photo bytes while an older cloud save is in flight, followed by sign-out
- Decorative account-nav avatars keep the You label/navigation; guest/missing/error fallback, logout, and late previous-account response protection

Reports, failed traces, and generated screenshot evidence are written to `test-results/account-drafts/` and `test-results/account-draft-results.json`.

## Verification limit

The cloud is a contract fake. Browser passes prove client/UI behavior and request shapes against this model; they do not prove hosted Supabase availability, production PostgreSQL/RLS behavior, Storage-service ownership metadata, or live migrations. The separate isolated SQL suite validates actual migration logic. No production-readiness claim should rely on this fixture alone.

## PostgreSQL tests

Install the pinned PGlite dependency declared in `qa/data-repairs/package.json`, then run:

```sh
node --test qa/account-drafts/sql/*.test.mjs
```

The optional `PGLITE_MODULE` environment variable may point to an already installed PGlite module. The SQL suite replays the repository baseline before migration `20261011000329`, then applies the reviewed component SQL and tests it. The production migration file mirrors the version generated by the connected migration service; it was not assigned an invented local timestamp.
